Targets that fail are queued for retry with exponential backoff. End users never see a half-published state.

Reference › Architecture
System Architecture


      

        
Three-tier topology

        

          
The console deliberately separates trust boundaries. The browser never holds a credential to a downstream system. All outbound API traffic originates from the gateway, which lives entirely on the internal network and is operated by Engineering.


          

            
          

        

      


      

        
Component responsibilities

        

          

            
ComponentOwnsDoes NOT

            
              

                Browser SPA
                UI, markdown editing, client-side validation, draft autosave to gateway
                Hold any 3rd-party API key. Talk directly to Knowledge Base/HubSpot/Custom Knowledge Management System.
              

              

                Publishing Gateway
                SSO+MFA verification, RBAC, request signing, transform pipeline, audit emission, CSRF, rate-limit, content scrubbing
                Persist secrets. Hold long-lived bearer tokens in memory.
              

              

                Worker Pool
                Outbound API calls to targets, retry with backoff, dead-letter queue, per-target circuit breakers
                Accept submissions directly from anything but the gateway.
              

              

                Secrets Vault
                Stores Knowledge Base API key, HubSpot per-function keys, Custom Knowledge Management System credential. Auto-rotation hooks.
                Be reachable from the user zone. Be queryable without a sealed-vault unseal.
              

              

                Postgres
                Drafts, document versions, publish history, queue state
                Hold the audit log alone — that is hash-chained and forwarded to SIEM.
              

            
          

        

      


      

        
Local deployment notes

        

          
Per the original requirement, the entire stack runs on internal infrastructure managed by Engineering. There is no SaaS dependency. The reference deployment is a single Docker Compose file:

          
# docker-compose.yml — reference layout, owned by Engineering
services:
  gateway:        # FastAPI; behind nginx + WAF
    image: aeglos/docsanctum-gateway:0.3
    env_file: /etc/docsanctum/gateway.env
    networks: [internal]
  worker:         # N replicas; pulls jobs from Postgres LISTEN/NOTIFY
    image: aeglos/docsanctum-worker:0.3
    deploy: { replicas: 4 }
    networks: [internal, egress-allowed]
  postgres:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
    networks: [internal]
  vault:          # sealed; unseal keys held by 2 of 3 engineers
    image: hashicorp/vault:1.16
    networks: [internal]
  proxy:
    image: nginx:1.27
    ports: ["443:443"]
    networks: [internal, edge]

networks:
  edge:           { driver: bridge }
  internal:       { internal: true }
  egress-allowed: { driver: bridge }   # only worker network reaches the internet

        

      

    


    
    

      
Reference › Security
Security Model


      

        Threat model summary
        The console multiplies blast radius. A single compromised author can corrupt knowledge across Knowledge Base, HubSpot Provider Alerts, and Custom Knowledge Management System simultaneously. The controls below exist specifically to keep that worst case from being silent.
      


      

        

          
Authentication & Session

          

            
    
              
  • SSO via existing IdP (SAML/OIDC) — no local password store. Inherits Aeglos MFA policy.
    • 
              
  • Step-up auth required at publish — re-prompt for password or TOTP. Session cookie alone is insufficient.
    • 
              
  • Session cookies: HttpOnly · Secure · SameSite=Strict · 8 hour absolute expiry, 30 minute idle.
    • 
              
  • Per-request CSRF token bound to session, rotated on privilege change.
    • 
              
  • No JWTs in localStorage. Ever.
    • 
            

          

        


        

          
Authorization (RBAC)

          

            

              
RoleCan do

              
                
ViewerRead drafts, library, history, audit (own actions only)

                
Editor+ Create/edit drafts, save, request review

                
Publisher+ Publish to non-partner targets (Custom Knowledge Management System, internal)

                
Partner Publisher+ Publish to specific partner namespaces only

                
Admin+ Manage targets, routing rules, RBAC, view full audit

              
            

          

        

      


      

        
Secrets handling

        

          
    
            
  • All downstream credentials (Knowledge Base API key, HubSpot per-function keys, Custom Knowledge Management System basic auth) live exclusively in the Vault. They are never in env files, container images, source, or browser storage.
    • 
            
  • Workers pull short-lived leases at job time. A leaked lease expires within minutes.
    • 
            
  • Vault is sealed; unseal requires 2-of-3 keys held by separate engineers.
    • 
            
  • Every secret read is logged to the audit chain.
    • 
            
  • API keys rotated at minimum quarterly; rotation is automated where the downstream supports it.
    • 
          

        

      


      

        
Input handling & transform safety

        

          
    
            
  • Markdown is parsed server-side (in the gateway, not the browser) using a hardened parser with HTML disabled. Raw HTML in author input is stripped, not sanitized — sanitization is a known historical XSS source.
    • 
            
  • Slugs are validated against ^[a-z0-9-]{3,80}$ before any URL construction.
    • 
            
  • All payloads to Knowledge Base / HubSpot are constructed from a typed schema, never string-templated. Injection attacks against downstream systems are eliminated by construction.
    • 
            
  • The gateway enforces a per-request size limit (256KB) and a per-author daily publish quota.
    • 
            
  • Outbound traffic is restricted at the network level — only the worker network can reach the internet, only on 443, only to allowlisted hostnames (kb.com.au, hubspot.example.com, kms.example.com).
    • 
          

        

      


      

        
Audit & non-repudiation

        

          
    
            
  • Every authenticated action is appended to a hash-chained log in Postgres before any external API call.
    • 
            
  • Each entry includes: timestamp (UTC, monotonic), actor, action, resource, request hash, prior-entry hash, source IP, user agent.
    • 
            
  • The chain is forwarded to the SIEM in near real-time. A successful gateway-only compromise cannot rewrite history without breaking the chain at the SIEM endpoint.
    • 
            
  • Audit log is read-only from the application. Direct DB writes from outside the gateway role are denied at the Postgres role level.
    • 
            
  • Author identity is preserved in the downstream payload (Knowledge Base feedback content, HubSpot Add Note text) so the BSS-side audit can be cross-referenced.
    • 
          

        

      


      

        
Failure-mode honesty

        

          
The console is explicit about partial-failure states because hiding them caused most of the duplicate-posting problem this is meant to solve.

          

            
ScenarioWhat happens

            
              
Knowledge Base down, HubSpot OKHubSpot Provider Alert publishes immediately. Knowledge Base job enters retry queue. Author is notified. Library shows partial-published state.

              
HubSpot down, Knowledge Base OKKnowledge Base publishes. HubSpot job enters retry queue. Author can manually post the alert via fallback link if urgent.

              
Gateway crashes mid-fan-outAudit entry exists, individual target jobs are atomic — on restart, jobs without success records are re-queued. Idempotency key on each target prevents duplicate posts.

              
Vault sealedWorkers cannot get credentials, jobs queue. Gateway returns 503 on publish attempts with a clear message. No silent failure.

            
          

        

      

    


    
    

      
Reference › Adapter Contract
Adapter Contract


      

        Why adapters?
        Each downstream system speaks a different dialect. Knowledge Base has rich record types but no native "broadcast." HubSpot has Provider Alerts and account-scoped Notes but no article schema. Custom Knowledge Management System is plain custom knowledge management system text. The adapter pattern keeps transform logic isolated, swappable, and individually testable. Adding a fifth target later doesn't require touching the others.
      


      

        
Knowledge Base Adapter kb@2.7

        
Source: kb Search API Reference v2.7 (15 July 2022)

        
Canonical document → Knowledge Base record. Maps document type 1:1 to Knowledge Base's native types. Authentication via x-api-key header.

        
    
          
  • Document Note → POST equivalent endpoint with { title, permalink, content (HTML), related_links[] }
    • 
          
  • Work Instruction → record with content.steps[] and content.links[] for branching flows
    • 
          
  • Hub → record with content.start_content, content.hub_links[], content.end_content
    • 
          
  • Compass → record with content.questions[], content.outcome_map[], content.outcomes[]
    • 
          
  • Announcement → posted via the announcements endpoint (/kb-api/announcements)
    • 
          
  • Idempotency: permalink slug serves as natural key; existing record with the same slug is updated, not duplicated.
    • 
          
  • Retry-safe: all operations use deterministic slugs; double-execution produces no duplicate.
    • 
        

      


      

        
HubSpot Adapter aeglos-hd@4.1.6

        
Source: Aeglos HubSpot API Development Guide v4.1.6 · Per-function keys

        
HubSpot is a BSS API (customer/service provisioning), not a knowledge base. The adapter routes a single canonical submission to the appropriate HubSpot surface based on type and routing rules. The most common operation for KB-style content is Add Provider Alert — the broadcast surface used by support staff.

        
    
          
  • Add Provider Alert (default for Document Note, Announcement, Work Instruction): builds a short alert payload with title, summary, deep-link to the Knowledge Base permalink, and severity inferred from tags (urgent → high).
    • 
          
  • Add Note (when document is account-scoped): attaches the document title + summary + Knowledge Base link as a customer/account note. Triggered when account-scoped tag is present and a customer ID is provided.
    • 
          
  • Add Ticket (manual override only): not used for ordinary KB publishing — available as an explicit author choice when documenting an active incident.
    • 
          
  • Hub / Compass: not published to HubSpot — the surface cannot represent them. The author is informed during preview.
    • 
          
  • Idempotency: client-side request ID echoed in the alert subject; the worker checks for an existing alert with the same ID before posting.
    • 
          
  • Footprint: deep-link points back to the Knowledge Base record so the alert never duplicates the body — it points to the canonical source.
    • 
        

      


      

        
Custom Knowledge Management System Adapter Custom Knowledge Management System@xmlrpc

        
XML-RPC custom knowledge management system.putPage · namespaced by partner

        
Read-only mirror for archival and on-prem search. Markdown is converted to Custom Knowledge Management System syntax via a deterministic transformer. Page namespace is derived from partner field.

        
    
          
  • Path: {partner_or_internal}:kb:{slug}
    • 
          
  • Idempotency: putPage is naturally idempotent on the namespace path.
    • 
          
  • Transform: Markdown → Custom Knowledge Management System via a pure function with golden-file tests (no external dependencies).
    • 
          
  • Failure handling: Custom Knowledge Management System failures never block other targets. The custom knowledge management system is treated as eventually-consistent.
    • 
        

      


      

        
Adapter interface (gateway-side, Python sketch)

        


# adapters/base.py
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class CanonicalDoc:
    id: str
    title: str
    slug: str
    type: str            # documentnote | workinstruction | hub | compass | announcement
    partner: str | None
    body_markdown: str
    tags: list[str]
    author: str
    change_note: str

@dataclass
class PublishResult:
    target: str
    ok: bool
    external_id: str | None
    error: str | None
    request_hash: str    # for audit chain
    duration_ms: int

class Adapter(ABC):
    name: str
    version: str

    @abstractmethod
    def can_publish(self, doc: CanonicalDoc) -> bool: ...

    @abstractmethod
    def transform(self, doc: CanonicalDoc) -> dict: ...

    @abstractmethod
    def publish(self, doc: CanonicalDoc, secret_lease) -> PublishResult: ...

    @abstractmethod
    def health_check(self) -> bool: ...
